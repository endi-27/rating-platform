# Протокол експериментів та аналіз результатів (ЛР №5)
## Навантажувальне тестування та System Performance Baseline

У цьому протоколі зафіксовано емпіричні метрики, зведені таблиці випробувань, визначення точки насичення (Saturation Point), аналіз масштабування та паспорт **System Performance Baseline** розподіленої платформи **Distributed Reviews & Ratings Platform** за результатами виконання комплексу навантажувальних тестів (k6 + автоматизований тестовий раннер `scripts/load_testing/run_baseline_suite.py`).

## 1. Специфікація випробувального контуру

Випробування проводилися в ізольованому багатоконтейнерному контурі Docker Compose за наступної апаратно-програмної конфігурації:

* **Балансувальник навантаження (Edge):** Nginx 1.27 (ліміт: `128MB RAM, 0.5 CPU`, `keepalive 65s`, алгоритм `round_robin` на 3 вузли).
* **Сервісний шар (Compute):** 3 stateless-екземпляри FastAPI 3.12+ (`rating_backend_1`, `rating_backend_2`, `rating_backend_3`), ліміт пам'яті `512MB RAM` на екземпляр, `asyncio` event loop.
* **Основна СУБД (Storage):** PostgreSQL 16 (`512MB RAM`, пул з'єднань `max_connections=150`, драйвер `asyncpg` з фіксованим пулом `pool_size=10, max_overflow=10`).
* **Розподілений кеш (In-Memory):** Redis 7 (`300MB RAM, 0.5 CPU`, том персистентності `redis_data`, RDB/AOF).
* **Двигун навантаження (Load Injector):** k6 v0.54 (Docker) та нативний асинхронний раннер `run_baseline_suite.py`.
* **Тестові сценарії:**
  * **Scenario A (Read-Intensive):** 70% `GET /api/v1/targets/{id}`, 30% `GET /api/v1/targets/{id}/rating` (Redis Cache-Aside).
  * **Scenario B (Write-Intensive):** 100% `POST /api/v1/targets/{id}/reviews` (JWT-автентифікація, перевірка бізнес-правил, транзакція `UnitOfWork`, оновлення `target_ratings`).
  * **Scenario C (Complex End-to-End Workflow):** Повний користувацький шлях: `GET /targets` (каталог) $\to$ `GET /targets/{id}` (деталі) $\to$ `POST /targets/{id}/reviews` (публікація відгуку) $\to$ `POST /reviews/{id}/vote` (голосування) $\to$ `GET /targets/{id}/rating` (верифікація перерахованого рейтингу).

## 3. Експеримент 2: Точка насичення (Saturation Point) та Primary Bottleneck

### Аналітична таблиця виходу на плато

| Навантаження | Throughput Scenario B (RPS) | Приріст RPS (%) | Latency Avg (мс) | Latency p95 (мс) | Стан системи |
| :---: | :---: | :---: | :---: | :---: | :--- |
| **10 VUs** | 11.65 RPS | — | 770.56 | 1241.61 | Лінійна зона (робоче навантаження) |
| **25 VUs** | **11.81 RPS** | **+1.37%** | **2052.71** | **2769.37** | **Saturation Point (Точка насичення / перегин)** |
| **50 VUs** | 11.09 RPS | -6.10% | 4226.62 | 4494.00 | Плато пропускної здатності, зростання черги |
| **100 VUs** | 11.90 RPS | +0.76% | 8178.32 | 8378.81 | Глибоке перевантаження черги (Little's Law) |
| **200 VUs** | 11.94 RPS | +0.34% | 16126.45 | 16693.24 | Деградація затримок до 16.7 с, нульовий приріст |

### Інженерне обґрунтування насичення

1. **Точка зламу (Saturation Point):** Досягається при **25 VUs** у Scenario B (Write) на рівні **11.81 RPS**. Подальше збільшення конкурентних клієнтів у 8 разів (до 200 VUs) **не призводить до збільшення продуктивності** ($\approx 11.9\text{ RPS}$), а викликає суто лінійне накопичення запитів у черзі згідно із **Законом Літтла** ($L = \lambda W$).
2. **Первинне вузьке місце (Primary Bottleneck):**
   * **Блокування рядків у PostgreSQL (Row-Level Lock Contention):** Усі паралельні транзакції запису відгуків до одного об'єкта конкурують за ексклюзивне оновлення агрегованого рядка в таблиці `target_ratings` (`SELECT ... FOR UPDATE` / `UPDATE target_ratings WHERE target_id = :id`).
   * **Вичерпання пулу з'єднань БД:** Затримки очікування блокувань утримують з'єднання `asyncpg` зайнятими на тривалий час, вичерпуючи ліміт пулу.
   * **Криптографічне навантаження на CPU:** Валідація JWT та операції хешування в асинхронному циклі FastAPI створюють конкуренцію за процесорні такти.
3. **Стабільність відмов:** Попри екстремальне зростання часу очікування (до 16.7 с при 200 VUs), рівень системних помилок склав **0.00%** (відсутність 500/502/504), що підтверджує надійність механізмів черг та транзакційних таймаутів.

## 4. Експеримент 3: Вплив горизонтального масштабування (Scaling Impact)

Порівняння продуктивності системи при фіксованому навантаженні **50 VUs** для Scenario A (Read) при конфігурації **1 вузол FastAPI** проти **3 вузлів FastAPI** за Nginx Round-Robin.

| Метрика конфігурації | 1 вузол FastAPI (`backend_1`) | 3 вузли FastAPI (`backend_1..3`) | Дельта / Ефект |
| :--- | :---: | :---: | :---: |
| **Throughput (RPS)** | **402.94 RPS** | **416.86 RPS** | **+3.45%** |
| **Latency Avg (мс)** | 113.59 мс | 109.14 мс | **-3.92% (покращення)** |
| **Latency p95 (мс)** | 438.58 мс | 425.34 мс | -3.02% |
| **Latency p99 (мс)** | 507.78 мс | 467.88 мс | -7.86% |
| **Error Rate (%)** | 0.00% | 0.00% | 0.00% |
| **Коефіцієнт масштабованості ($S$)** | — | **1.03x** | $S = \text{RPS}_3 / \text{RPS}_1$ |
| **Ефективність кластера ($E$)** | 100% | **34.33%** | $E = S / 3$ |

### Висновки щодо масштабування
На єдиному фізичному хості в середовищі віртуалізації Docker Compose додавання 3 екземплярів сервісного шару збільшує пропускну здатність лише у **1.03 раза** ($+3.45\%$). Причиною є спільне споживання ресурсів фізичного процесора (CPU contention) між трьома процесами Uvicorn та спільними контейнерами Nginx, Redis і PostgreSQL. Справжнє лінійне масштабування потребує рознесення екземплярів на окремі фізичні сервери або масштабування шарду сховища.

## 5. Експеримент 4: Вплив кешування (Caching Impact: Cold vs Warm Cache)

Порівняння читання при навантаженні **50 VUs** для Scenario A у двох станах кешу:
1. **Warm Cache:** Redis розігрітий, 100% потраплянь (`X-Cache: HIT`).
2. **Cold Cache:** Кеш очищено (`FLUSHDB`), пряме читання з PostgreSQL 16 (`X-Cache: MISS`).

| Параметр випробування | Warm Cache (Redis HIT) | Cold Cache (Postgres Direct) | Відхилення |
| :--- | :---: | :---: | :---: |
| **Throughput (RPS)** | 397.19 RPS | 411.32 RPS | -3.44% |
| **Latency Avg (мс)** | 116.13 мс | 111.85 мс | +3.83% |
| **Latency p50 (мс)** | 82.62 мс | 54.37 мс | +51.9% |
| **Latency p95 (мс)** | 379.20 мс | 365.96 мс | +3.62% |
| **Latency p99 (мс)** | 468.49 мс | 397.31 мс | +17.9% |
| **Speedup Ratio** | **0.96x** | 1.00x | Накладні витрати TCP сокета Redis |
| **Розвантаження СУБД (Query Offload)** | **100% захист від I/O** | 0% (усі запити в БД) | Усунення навантаження на диск БД |

### Висновки щодо кешування
При невеликому розмірі вибірки на синтетичному мікро-бенчмарку сторінки БД повністю перебувають у `shared_buffers` PostgreSQL в оперативній пам'яті, тому мережевий оверхед звернення через TCP-сокет до Redis (`SafeRedisBackend` + серіалізація JSON) демонструє приблизно однаковий час виконання. Проте в реальних умовах експлуатації з мільйонами рядків відгуків Redis відіграє критичну роль захисного бар'єра, ізолюючи диск та з'єднання PostgreSQL від деградації.

## 7. Підсумкові інженерні висновки

1. **Базова пропускна здатність на читання:** Платформа демонструє максимальну стабільну продуктивність **505.89 RPS** при затримці $p95 = 35.27\text{ мс}$ (10 VUs). При зростанні до 200 VUs система утримує Throughput на рівні $\approx 436\text{ RPS}$ без жодної помилки ($0.0\%$ Error Rate).
2. **Асиметрія операцій читання та запису:** Операції запису (Scenario B) мають пропускну здатність у $\approx 42$ рази нижчу за операції читання (**11.81 RPS** проти **505.89 RPS**), що є класичною ознакою транзакційної реляційної моделі з агрегацією.
3. **Підтвердження точки насичення:** Межею стабільності запису є 25 VUs. Подальше навантаження не дає додаткового RPS, а лише формує чергу затримок.
4. **Вектор подальших оптимізацій:**
   * Розподіл трафіку читання/запису на рівні СУБД (Read Replica) — ЛР №6;
   * Горизонтальне шардування за `shard_key=target_id` для рознесення блокувань `target_ratings` — ЛР №7;
   * Застосування оптимістичного блокування (OCC) без блокуючих `SELECT FOR UPDATE` — ЛР №8.
